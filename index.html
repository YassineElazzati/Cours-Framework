Pourquoi cette séance

Le chaînon manquant entre ce que vous savez déjà et ce qui vous attend.

Vous savez aujourd'hui faire trois choses, et vous les faites séparément. Vous savez modéliser un domaine et le traduire en tables PostgreSQL. Vous savez interroger ces tables en SQL. Vous savez écrire des classes Java qui manipulent des objets.

Ce que personne ne vous a encore expliqué, c'est comment on assemble ces trois compétences dans une seule application, et pourquoi tout le monde les assemble à peu près de la même manière. Cette manière porte un nom : une architecture. L'outil qui vous la propose — ou vous l'impose — porte un nom : un framework. Et la porte d'entrée par laquelle le monde extérieur s'adresse à votre application porte un nom : une API.

🎯 L'objectif du jour

À la fin de cette séance, vous devez pouvoir lire une offre d'emploi qui dit « architecture n-tiers, Spring MVC, couche service, repository JPA, API REST » et comprendre chaque mot. Pas savoir l'écrire — le comprendre.

Bibliothèque ou framework ?

La différence n'est pas une question de taille. C'est une question de qui commande.

La boîte à outils et la maison préfabriquée

Métaphore du chantier

Vous devez construire une maison.

Première option : la boîte à outils. On vous livre un marteau, une scie, une perceuse. Excellents outils. Mais vous décidez de tout : où poser les fondations, quand monter les murs, dans quel ordre. Vous prenez le marteau quand vous en avez besoin, et vous le reposez. Vous êtes le chef de chantier.

Seconde option : la maison préfabriquée. On vous livre une structure déjà debout : murs porteurs, dalle, gaines électriques, arrivées d'eau. Vous n'avez plus qu'à aménager l'intérieur, aux emplacements prévus. Vous gagnez six mois. Mais vous ne mettez pas la salle de bain où vous voulez : les arrivées d'eau sont déjà là.

La boîte à outils, c'est une bibliothèque. La maison préfabriquée, c'est un framework.

Une bibliothèque (library) est un ensemble de classes et de fonctions déjà écrites, que vous appelez quand vous en avez besoin. Vous gardez la main sur le déroulement du programme.

Un framework — le mot se traduit par « cadre de travail », « ossature » — est un squelette d'application déjà construit, qui appelle votre code aux moments qu'il a prévus. C'est lui qui garde la main.

Le même travail, vu des deux côtés

// ── BIBLIOTHÈQUE : c'est MOI qui appelle ────────────────────
public class Programme {
    public static void main(String[] args) {
        Client client = new Client("Dupont");   // mon code
        String json = new Gson().toJson(client);   // j'appelle la biblio
        System.out.println(json);                    // je reprends la main
    }
}

Gson est une bibliothèque de conversion en JSON. Je l'appelle, elle répond, je continue.

// ── FRAMEWORK : c'est LUI qui m'appelle ─────────────────────
@RestController
public class ClientController {

    @GetMapping("/clients")              // « appelle-moi sur cette URL »
    public List<Client> lister() {       // je n'appelle JAMAIS cette méthode
        return service.tousLesClients();
    }
}

⚠️ Le piège du vocabulaire

« Framework » n'est pas un synonyme de « grosse bibliothèque ». Un framework peut être petit, une bibliothèque peut être énorme. Le seul critère qui tranche est celui du sens de l'appel : si c'est vous qui appelez, c'est une bibliothèque ; si c'est lui qui vous appelle, c'est un framework.

L'inversion de contrôle

Le chantier, suite

Sur un chantier ordinaire, le plombier arrive quand il veut, pose ses tuyaux, s'en va. Résultat : il passe avant le maçon, le maçon casse ses tuyaux, tout est à refaire.

Sur un chantier organisé, il y a un chef de chantier. Le plombier lui laisse son numéro et rentre chez lui. Le chef l'appelle le jour où c'est son tour. Le plombier a perdu la liberté de décider quand il travaille. Il a gagné une maison qui tient debout.

Ce renversement porte un nom : l'inversion de contrôle (Inversion of Control, IoC). Dans un programme classique, votre code décide de l'enchaînement et appelle les outils. Avec un framework, l'enchaînement appartient au framework, et c'est lui qui vient chercher vos morceaux de code.

On résume ce principe par une formule empruntée aux castings de cinéma, le principe d'Hollywood : « Ne nous appelez pas, nous vous appellerons. » Vous laissez vos coordonnées — vos annotations — et vous attendez.

⚠️ IoC et injection de dépendances ne sont pas synonymes

L'inversion de contrôle est un principe général : le contrôle du flux passe à un cadre extérieur. L'injection de dépendances (Dependency Injection, DI) n'en est qu'une technique de mise en œuvre parmi d'autres. Tout DI est de l'IoC ; tout IoC n'est pas du DI. Confondre les deux est l'erreur la plus fréquente en entretien d'embauche.

Ce qu'un framework vous donne, ce qu'il vous prend

Un framework n'est pas gratuit. Le choisir est un arbitrage, pas un réflexe.

Ce qu'il vous donneCe qu'il vous prend
Du temps. Connexion à la base, sécurité, gestion des erreurs, serveur web : tout est déjà écrit.Du temps, d'abord. Apprendre Spring prend des semaines. Sur un script de 200 lignes, vous perdez au change.
Des conventions. Un développeur qui arrive sur votre projet retrouve ses repères en une heure.De la liberté. On fait les choses à la manière du framework, ou on souffre.
Du code éprouvé. Des milliers de projets ont déjà trouvé les bugs à votre place.De la transparence. Beaucoup de choses se passent « toutes seules ». Quand ça casse, il faut savoir pourquoi.
Un écosystème. Documentation, forums, modules, recrutement.De l'indépendance. C'est l'enfermement propriétaire (vendor lock-in) : en sortir coûte cher.
💡 La règle de décision

Un framework est rentable quand le projet est durable, collectif et standard. Une application de gestion sur trois ans, à cinq développeurs : oui. Un script d'import lancé une fois : non, une bibliothèque suffit.

Les principes de conception

Une architecture n'est pas un goût personnel. C'est la réponse à quatre ou cinq principes.

La séparation des responsabilités

Métaphore du restaurant — on la garde jusqu'à la fin

Dans un restaurant qui tourne, personne ne fait tout. Le serveur prend les commandes et apporte les assiettes ; il ne cuisine pas. Le cuisinier prépare ; il ne va jamais en salle. Le magasinier gère le stock ; il ne touche ni aux clients ni aux casseroles.

Imaginez maintenant l'inverse : un seul employé qui prend la commande, court en cuisine, redescend en réserve, remonte, ressert. Aux heures creuses, ça marche. À midi, tout s'effondre. Et le jour où il tombe malade, le restaurant ferme.

La séparation des responsabilités (separation of concerns) consiste à découper un programme en parties qui ont chacune un seul métier. Une partie affiche. Une partie décide. Une partie stocke. Aucune ne fait le travail d'une autre.

Voici ce que donne le non-respect de ce principe. Ce code fonctionne, et c'est bien le problème :

// ❌ Une seule méthode qui fait TOUT : afficher, décider, stocker
public void inscrire(String nom, int age) {
    if (age < 18) {                                  // règle métier
        System.out.println("Refusé : mineur");      // affichage
        return;
    }
    Connection c = DriverManager.getConnection(...); // accès base
    c.prepareStatement("INSERT INTO client ...").execute();
    System.out.println("Bienvenue " + nom);          // affichage
}

Analysons ce code ligne par ligne :

  • if (age < 18) — une règle métier. Elle appartient au domaine, pas à l'écran.
  • System.out.println — de l'affichage, en console. Le jour où l'application devient un site web, cette ligne ne sert plus à rien.
  • DriverManager.getConnection — de l'accès aux données, écrit en dur. Changer de base oblige à rouvrir cette méthode.

Trois métiers en huit lignes. Conséquence concrète : cette règle des 18 ans est intestable sans base de données allumée, et irréutilisable ailleurs.

Couplage et cohésion

La guirlande et le tiroir

Le couplage, c'est la vieille guirlande de Noël montée en série : une ampoule grille, tout s'éteint, et vous passez la soirée à chercher laquelle. Les guirlandes modernes sont en parallèle : une ampoule grille, les autres continuent.

La cohésion, c'est le tiroir à couverts : fourchettes avec fourchettes, couteaux avec couteaux. Son contraire est le tiroir fourre-tout de la cuisine, où cohabitent des piles, du scotch, une clé sans serrure et trois vis.

Le couplage mesure à quel point deux parties du code dépendent l'une de l'autre. La cohésion mesure à quel point les éléments d'une même partie vont réellement ensemble.

🎯 La formule à retenir

Couplage faible, cohésion forte. Chaque module s'occupe d'une seule chose (cohésion forte) et dépend le moins possible des autres (couplage faible). Toute l'architecture logicielle tient dans ces quatre mots.

DRY, KISS, YAGNI

SigleCe qu'il ditL'image

⚠️ DRY mal compris fait plus de mal que bien

Deux morceaux de code qui se ressemblent ne sont pas forcément des doublons. DRY parle de connaissance dupliquée, pas de caractères dupliqués. Le calcul d'une TVA et celui d'une remise peuvent s'écrire pareil : les fusionner en une seule méthode vous garantit une catastrophe le jour où la TVA change.

SOLID en cinq phrases

SOLID est un moyen mnémotechnique pour cinq principes de conception orientée objet. Deux d'entre eux vous serviront dès la semaine prochaine ; retenez surtout ceux-là.

Le « D », en détail — c'est lui qui prépare Spring

La prise électrique

Votre lampe de bureau ne connaît pas la centrale nucléaire. Elle ne connaît qu'une chose : une prise à deux trous, 230 volts. C'est un contrat standard. Derrière la prise, on peut passer du nucléaire à l'éolien sans que la lampe s'en aperçoive — et vous pouvez brancher n'importe quelle lampe.

La prise, c'est l'interface. La lampe ne dépend pas d'un producteur d'électricité : elle dépend d'une prise.

// ❌ COUPLAGE FORT — le service fabrique lui-même sa dépendance
public class ServiceClient {
    private ClientDaoPostgres dao = new ClientDaoPostgres();
    //      ↑ soudé à PostgreSQL, pour toujours
}

// ✅ INVERSION DES DÉPENDANCES — on dépend d'un contrat
public interface ClientDao {              // la « prise »
    Client trouverParId(Long id);
}

public class ServiceClient {
    private final ClientDao dao;           // une interface, pas une classe

    public ServiceClient(ClientDao dao) {   // on ME donne l'implémentation
        this.dao = dao;
    }
}

Analysons ce code ligne par ligne :

  1. new ClientDaoPostgres() — la classe fabrique elle-même son outil. Elle est soudée à PostgreSQL : impossible de la tester sans base réelle, impossible de changer de stockage.
  2. interface ClientDao — on déclare le contrat : « quelqu'un, quelque part, sait retrouver un client par son identifiant ». On ne dit pas comment.
  3. private final ClientDao dao — le service ne connaît plus que le contrat. final garantit que la dépendance ne changera pas en cours de route.
  4. public ServiceClient(ClientDao dao) — la dépendance entre par le constructeur. Le service ne la fabrique plus : on la lui fournit. C'est exactement ce que Spring automatisera.
💡 Le test qui ne ment pas

Posez-vous cette question devant n'importe quelle classe : « puis-je la tester sans allumer la base de données ? » Si la réponse est non, le couplage est trop fort. Avec la seconde version, il suffit de passer une fausse implémentation de ClientDao qui renvoie un client inventé.

L'architecture en couches

Le découpage que vous retrouverez dans neuf applications de gestion sur dix.

Les trois étages du restaurant

Le restaurant, suite

Trois espaces, trois métiers, une circulation stricte :

La salle — le serveur accueille, prend la commande, apporte l'assiette. Il ne décide pas de la recette et ne descend jamais en réserve.

La cuisine — on applique les recettes, on refuse un plat si un ingrédient manque, on décide qu'un plat n'est pas servi le dimanche. C'est là que sont les règles.

La réserve — on range, on retrouve, on sort les ingrédients. Aucune décision : on stocke et on rend ce qu'on demande.

Et surtout : le client ne va jamais en réserve. Il parle au serveur, qui parle à la cuisine, qui parle à la réserve. Chacun ne s'adresse qu'à son voisin immédiat.

🎯 La règle de circulation

Chaque couche ne parle qu'à celle du dessous. La présentation appelle le métier, le métier appelle la persistance. Jamais l'inverse, et jamais de saut : un contrôleur qui écrit du SQL est une faute d'architecture, même si le code fonctionne.

Le vocabulaire des couches

Ces cinq mots reviendront chaque jour à partir de la semaine prochaine. Ce sont des rôles, pas des mots-clés du langage : ce sont de simples classes Java.

// Le même besoin, traversant les trois couches

// ── PRÉSENTATION : je reçois, je délègue, je renvoie ─────────
public class ClientController {
    private final ClientService service;

    public ClientDto fiche(Long id) {
        Client client = service.trouverParId(id);   // je délègue
        return ClientDto.depuis(client);            // je masque les champs privés
    }
}

// ── MÉTIER : je décide ───────────────────────────────────────
public class ClientService {
    private final ClientRepository repository;

    public Client trouverParId(Long id) {
        Client c = repository.findById(id);
        if (c == null) throw new ClientIntrouvable(id); // règle métier
        return c;
    }
}

// ── PERSISTANCE : je range et je retrouve ────────────────────
public interface ClientRepository {
    Client findById(Long id);
    void save(Client client);
}

Analysons ce code ligne par ligne :

  1. Le contrôleur ne contient aucune décision. Il traduit une demande extérieure en appel de service, puis traduit le résultat en objet de sortie.
  2. Le service décide : ici, « un client introuvable est une erreur ». C'est une règle du domaine, elle vit donc au milieu.
  3. Le repository est une interface — un contrat. On applique le « D » de SOLID : le service dépend d'un contrat, pas d'une implémentation PostgreSQL.
  4. Chaque couche ne connaît que la suivante. Le contrôleur ignore jusqu'à l'existence du repository.

Où atterrissent vos MCD, MLD et MPD

📝 Rappel des séances de modélisation

Vous avez descendu trois marches : le MCD décrit le monde réel (entités, associations, cardinalités) ; le MLD le traduit en tables et clés étrangères ; le MPD le concrétise dans un SGBD précis (types PostgreSQL, index, contraintes).

Il vous manquait la quatrième marche : comment cette table redevient un objet Java.

-- MPD : la table telle qu'elle existe dans PostgreSQL
CREATE TABLE client (
    id                SERIAL PRIMARY KEY,
    nom               VARCHAR(50)  NOT NULL,
    email             VARCHAR(120) UNIQUE,
    date_inscription  DATE         NOT NULL
);
// La même réalité, vue depuis Java : une classe « entité »
public class Client {
    private Long id;                  // ↔ colonne id
    private String nom;               // ↔ colonne nom
    private String email;             // ↔ colonne email
    private LocalDate dateInscription; // ↔ colonne date_inscription
    // + constructeur, getters, setters
}

Écrire cette traduction à la main, table par table, colonne par colonne, est fastidieux et répétitif. C'est exactement le travail que fera l'ORM — voir section 10.

⚠️ Une entité n'est pas un DTO

L'entité est le reflet fidèle de la table : elle contient tout, y compris le mot de passe haché, la note interne du commercial, l'identifiant technique. Le DTO est ce qu'on accepte de montrer à l'extérieur.

Renvoyer directement une entité dans une réponse web est la fuite de données la plus banale du métier. En réserve, il y a le carton entier ; en salle, on apporte une assiette.

💡 Reconnaître une bonne couche métier

Ouvrez une classe de service et cherchez les mots SELECT, HttpServletRequest, System.out. Si vous en trouvez, une couche déborde sur une autre. Une couche métier propre ne parle que le langage du domaine : clients, commandes, remises, factures.

MVC, MVP, MVVM

Trois manières d'organiser l'écran. Ce ne sont pas des architectures rivales : ce sont trois façons de découper la couche de présentation.

⚠️ La confusion à dissiper tout de suite

MVC n'est pas une alternative à l'architecture en couches. MVC organise la couche présentation ; les couches organisent l'application entière. Une application Spring normale est en trois couches et en MVC. Les deux cohabitent, ils ne se remplacent pas.

MVC — Modèle, Vue, Contrôleur

Le service en salle

Vous commandez. Le serveur note, porte le bon en cuisine, revient avec l'assiette et la pose sur la table. La cuisine a préparé le plat sans jamais vous voir. La table présente le plat sans rien savoir de la recette.

Le serveur est le contrôleur, la cuisine est le modèle, la table est la vue.

ÉlémentResponsabilitéCe qu'il ignore
ModèleLes données et les règles métierIl ignore totalement l'existence d'un écran
VueL'affichage. Elle lit le modèle et le met en formeElle ne contient aucun calcul, aucune décision
ContrôleurRecevoir l'action, appeler le modèle, choisir la vueIl n'affiche rien et ne calcule rien
 
// LE CONTRÔLEUR — il n'affiche rien, il ne calcule rien
public class ClientController {

    private final ClientService service;   // le lien vers la cuisine

    public String afficherFiche(Long id, Modele modele) {
        Client client = service.trouverParId(id); // 1. je passe la commande
        modele.ajouter("client", client);        // 2. je pose le plat sur le passe
        return "fiche-client";                   // 3. je désigne la table
    }
}

Analysons ce code ligne par ligne :

  1. service.trouverParId(id) — le contrôleur délègue. Il ne sait pas comment on trouve un client, il sait à qui demander.
  2. modele.ajouter("client", client) — il dépose le résultat dans un sac de données que la vue viendra ouvrir. C'est le passe-plat.
  3. return "fiche-client" — il renvoie un simple texte : le nom de la vue à utiliser. Il ne génère pas une ligne de HTML lui-même.
⚠️ Le « M » de MVC n'est pas la base de données

Le modèle, ce sont les données et les règles du domaine, pas les tables PostgreSQL. Dans une application en couches, le « M » de MVC recouvre en pratique la couche métier et la couche persistance réunies, vues depuis la présentation.

MVP — Modèle, Vue, Présentateur

Le serveur qui dresse à table

Variante du service : le serveur ne se contente plus de poser l'assiette. Il apporte les éléments et dresse le plat devant vous, morceau par morceau. La table, elle, ne fait strictement rien : elle subit.

Dans MVP, la vue devient passive. Elle n'a plus le droit de lire le modèle. Le présentateur lui dicte tout, champ par champ : « écris Dupont dans le libellé du nom ».

// La VUE est réduite à un contrat d'affichage pur
public interface VueFicheClient {
    void afficherNom(String nom);
    void afficherErreur(String message);
}

// LE PRÉSENTATEUR pilote la vue instruction par instruction
public class PresentateurClient {
    private final VueFicheClient vue;      // il tient la vue
    private final ClientService service;

    public void charger(Long id) {
        try {
            Client c = service.trouverParId(id);
            vue.afficherNom(c.getNom());       // il DICTE l'affichage
        } catch (ClientIntrouvable e) {
            vue.afficherErreur("Client inconnu");
        }
    }
}

L'intérêt est le test : la vue étant une simple interface, on la remplace par une fausse implémentation et on vérifie que le présentateur a bien appelé afficherErreur. Aucun écran nécessaire.

MVVM et la liaison de données

Le passe-plat automatique

Dernière évolution du restaurant : on installe un tapis roulant entre la cuisine et la table. Dès qu'un plat est prêt, il apparaît devant vous. Personne ne le porte. Et dans l'autre sens : dès que vous posez votre carte de fidélité sur la table, la cuisine le sait immédiatement.

Plus personne ne fait le trajet. Le tapis est branché une fois pour toutes.

Ce tapis roulant s'appelle la liaison de données (data binding), et c'est la seule vraie différence entre MVVM et les deux précédents.

Le ViewModel — « modèle de vue » — expose l'état de l'écran et les données mises en forme. Il ne connaît pas la vue et ne l'appelle jamais. La vue se branche dessus.

<!-- LA VUE : aucune logique, uniquement des branchements -->
<input v-model="nom">                  <!-- liaison à double sens -->
<p>Bonjour {{ nomEnMajuscules }}</p>  <!-- liaison en lecture -->
// LE VIEWMODEL : l'état de l'écran, sans aucune référence à la vue
data() {
  return { nom: "" };                    // l'état
},
computed: {
  nomEnMajuscules() {
    return this.nom.toUpperCase();       // recalculé tout seul
  }
}

Analysons ce code ligne par ligne :

  1. v-model="nom" — la double liaison : l'utilisateur tape, l'attribut nom change instantanément ; on modifie nom par programme, le champ se met à jour. Aucun code pour ça.
  2. {{ nomEnMajuscules }} — la vue affiche une valeur calculée sans savoir comment elle est calculée.
  3. nomEnMajuscules() — cette fonction est rejouée automatiquement à chaque changement de nom. Personne ne l'appelle : le framework observe.
  4. Nulle part le ViewModel ne dit vue.afficher(...). Il ignore qu'une vue existe. C'est là toute la différence avec MVP.
⚠️ Le vrai critère de distinction

On lit souvent « MVC pour le web, MVVM pour le desktop ». C'est faux et ça ne vous aidera pas. Le critère réel est unique : y a-t-il une liaison de données automatique ? Si le framework observe les changements et rafraîchit l'écran seul, vous êtes en MVVM. Sinon, vous êtes en MVC ou MVP, quel que soit le support.

🎯 Ce qu'ils ont tous en commun

Les trois patrons répondent à la même question : comment empêcher que la logique métier se retrouve mélangée au code d'affichage ? Ils diffèrent seulement sur la façon dont la vue et les données communiquent. Retenez le problème, les solutions se déduisent.

💡 Vous ne choisirez presque jamais

En pratique, le patron vous est imposé par l'outil : Spring MVC vous met en MVC, Vue et Angular vous mettent en MVVM. L'enjeu n'est donc pas de choisir, mais de reconnaître dans quel patron vous êtes pour savoir où poser chaque ligne de code.

Les architectures d'ensemble

On change d'échelle : non plus l'organisation du code, mais celle de l'application entière.

Monolithe, monolithe modulaire, microservices

Le grand magasin et la rue commerçante

Le grand magasin : tout sous un seul toit, une seule caisse, un seul système d'alarme. Simple, efficace, et l'on circule d'un rayon à l'autre sans sortir. Mais pour repeindre le rayon jouets, on ferme tout le magasin. Et si le courant saute, plus rien ne fonctionne.

La rue commerçante : boulangerie, boucherie, librairie. Chacune son local, sa caisse, ses horaires. La boulangerie ferme pour travaux, les autres continuent. Mais désormais, pour un repas complet, il faut faire quatre boutiques sous la pluie — et si la boucherie déménage sans prévenir, le restaurateur d'à côté est en difficulté.

⚠️ Les microservices ne sont pas « la version moderne »

Ce n'est pas un progrès technique, c'est un arbitrage organisationnel. On accepte une complexité d'exploitation considérable — réseau, latence, pannes partielles, cohérence des données, supervision — en échange de l'autonomie de plusieurs équipes. Sur un projet à cinq développeurs, ce marché est perdant.

La recommandation courante du métier reste : commencez par un monolithe modulaire, et ne découpez que lorsque la douleur devient réelle et identifiée.

Couches ou tiers ?

Les deux mots se ressemblent, on les confond en permanence, et ils ne parlent pas de la même chose.

🎯 La phrase qui résume

Une application peut très bien être en trois couches et déployée sur un seul tier : trois paquets Java bien rangés dans un unique fichier installé sur une seule machine. Couches et tiers sont deux axes indépendants.

Architecture hexagonale

L'adaptateur de voyage

Votre ordinateur portable fonctionne en France, au Japon et au Brésil. Vous ne changez pas d'ordinateur : vous changez d'adaptateur. L'ordinateur définit ce dont il a besoin ; le monde extérieur s'y branche.

L'architecture hexagonale, aussi appelée ports and adapters — « ports et adaptateurs » — et proche de la Clean Architecture, pousse l'inversion des dépendances à son terme. Le code métier est placé au centre et ne dépend de rien. Autour, des adaptateurs : un pour le web, un pour PostgreSQL, un pour l'envoi d'e-mails.

💡 Pour l'instant, retenez juste l'idée

L'hexagonal est un sujet de deuxième année de pratique. Ce que vous devez en garder aujourd'hui : c'est le même principe que le « D » de SOLID vu en 3.4, appliqué à l'application entière au lieu d'une seule classe.

Qu'est-ce qu'une API ?

Le mot est partout, il est rarement défini. C'est pourtant l'un des plus simples du métier.

La carte du restaurant

Le restaurant, encore

Vous entrez dans un restaurant. Vous n'allez pas en cuisine choisir vos ingrédients : on vous tend la carte.

La carte vous dit trois choses, et seulement trois : ce que vous pouvez demander (les plats disponibles), comment le demander (« saignant ou à point ? »), et ce que vous allez recevoir (une description du plat). Elle ne vous dit pas la recette, ni la marque du four, ni le fournisseur de viande.

C'est exactement une API : la carte d'un programme.

API est le sigle de Application Programming Interface, en français interface de programmation applicative. C'est l'ensemble des points d'entrée qu'un programme expose pour que d'autres programmes s'en servent — sans jamais avoir à connaître son fonctionnement interne.

Une API se définit toujours par trois éléments :

Élément du contratAu restaurantDans une API web
Ce qu'on peut demanderLa liste des platsLa liste des adresses : /clients, /commandes
Comment le demander« Cuisson ? Entrée ou plat ? »Le verbe HTTP, les paramètres, le corps de la requête
Ce qu'on reçoitLa description du platLe format de la réponse : JSON, avec tels champs
🎯 La définition en une phrase

Une API, c'est un contrat : ce que je promets d'accepter, et ce que je promets de renvoyer. Tout le reste — le langage, la base de données, les algorithmes — est caché derrière, et peut changer sans prévenir tant que le contrat est respecté.

Vous en écrivez déjà sans le savoir

📝 Rappel du cours de POO Java

Quand vous écrivez public devant une méthode et private devant un attribut, vous êtes en train de définir une API. L'ensemble des membres public d'une classe est son API : c'est ce que le monde extérieur a le droit d'appeler. Le private est la cuisine.

public class CompteBancaire {

    private double solde;                    // LA CUISINE — invisible du dehors
    private List<Operation> historique;    // invisible aussi

    // ── L'API de cette classe : ce que les autres peuvent appeler ──
    public void deposer(double montant) { ... }
    public boolean retirer(double montant) { ... }
    public double getSolde() { ... }
}

Analysons ce code ligne par ligne :

  1. private double solde — personne à l'extérieur ne peut modifier le solde directement. On ne rentre pas en cuisine changer le contenu de la casserole.
  2. public void deposer(double montant) — un point d'entrée du contrat. Le nom, les paramètres et le type de retour sont le contrat.
  3. public boolean retirer(...) — le contrat annonce même son résultat : un booléen, donc « ça peut échouer ». Le code appelant sait à quoi s'attendre sans lire l'intérieur.
  4. Demain, vous pouvez réécrire entièrement l'intérieur de retirer : tant que la signature ne bouge pas, aucun code appelant ne casse.

Une API web, c'est le même principe, franchi d'un cran : au lieu d'exposer des méthodes à d'autres classes du même programme, on expose des adresses à d'autres programmes, à travers le réseau.

Une API n'est ni un serveur, ni une base de données, ni un langage. C'est une porte et son mode d'emploi. La très grande majorité des API dont on parle aujourd'hui sont des API web, mais l'API de la classe String est une API tout aussi authentique.

Un contrat, ça ne se casse pas

Puisqu'une API est un contrat, le modifier engage tous ceux qui l'utilisent. On appelle rupture de compatibilité (breaking change) toute modification qui casse le code des clients existants.

💡 D'où le numéro de version dans les adresses

C'est la raison pour laquelle vous voyez si souvent /api/v1/clients. Quand un changement casse le contrat, on n'écrase pas l'ancien : on publie /api/v2/clients à côté, et on laisse aux clients le temps de migrer. Comme un restaurant qui garde l'ancienne carte quelques mois.

L'API REST

La forme d'API web que vous rencontrerez dans la quasi-totalité des projets.

Le distributeur automatique

Métaphore du distributeur

Un distributeur automatique ne vous reconnaît pas. Il ne se souvient pas que vous êtes déjà passé ce matin, ni de ce que vous aviez choisi. Chaque achat doit contenir tout le nécessaire : la pièce et le code du produit.

C'est une contrainte pour vous. C'est une libération pour l'exploitant : il peut en installer dix identiques dans le hall, sans qu'ils aient besoin de se parler. N'importe lequel peut vous servir.

REST — REpresentational State Transfer — est un style d'architecture pour les API web, décrit en 2000 par Roy Fielding. Ce n'est ni un protocole, ni une bibliothèque, ni un standard imposé : c'est un ensemble de conventions qui s'appuient sur HTTP.

Quatre principes suffisent pour votre niveau :

PrincipeCe qu'il impose
Tout est ressourceChaque chose manipulable a une adresse : un client, une commande, une facture
Le verbe dit l'actionL'adresse nomme la chose, le verbe HTTP dit ce qu'on lui fait
Sans état (stateless)Chaque requête se suffit à elle-même. Le serveur ne retient rien entre deux appels
Une représentationOn n'échange pas l'objet, mais une représentation : le plus souvent du JSON
⚠️ « REST » est employé à tort et à travers

L'immense majorité des API dites « REST » ne respectent qu'une partie des critères de Fielding. Dans le métier, « API REST » signifie en pratique : API web en HTTP, avec des URL de ressources, des verbes HTTP et du JSON. C'est ce sens-là que vous utiliserez, et il est admis.

La ressource et son adresse

Une ressource est une chose, désignée par un nom, au pluriel, dans l'adresse (URL). Jamais un verbe.

AdresseCe qu'elle désigne
/clientsLa collection de tous les clients
/clients/42Un client précis, celui d'identifiant 42
/clients/42/commandesLes commandes de ce client — la jointure, vue de l'extérieur
/clients?ville=Lyon&page=2La collection filtrée et paginée : les filtres passent en paramètres, pas dans le chemin
⚠️ Un verbe dans l'URL est une faute

On n'écrit pas GET /supprimerClient?id=42, ni POST /creerClient. On écrit DELETE /clients/42 et POST /clients. Le verbe est déjà porté par HTTP : le répéter dans l'adresse est le signe d'une API mal conçue, et c'est la première chose qu'un correcteur regarde.

💡 Trois conventions qui font sérieux

Pluriel pour les collections (/clients, pas /client) · minuscules et tirets (/bons-de-commande) · numéro de version en tête (/api/v1/...).

Les verbes HTTP, CRUD et SQL

Voici le tableau qui relie tout ce que vous savez déjà. CRUD est l'acronyme des quatre opérations élémentaires sur une donnée : Create, Read, Update, Delete — créer, lire, modifier, supprimer.

⚠️ POST et PUT ne sont pas interchangeables

POST /clients crée : appelé trois fois, il crée trois clients. PUT /clients/42 remplace : appelé trois fois, le résultat est identique à un seul appel. Cette propriété s'appelle l'idempotence — « le même effet, quel que soit le nombre d'appels ». GET, PUT et DELETE sont idempotents ; POST ne l'est pas.

Anatomie d'une requête et d'une réponse

Analysons cette requête ligne par ligne :

  1. POST /api/v1/clients — le verbe et la ressource. À eux deux, ils disent tout : « ajoute un élément à la collection des clients ».
  2. Content-Type: application/json — un en-tête. Il annonce le format du corps envoyé, pour que le serveur sache le décoder.
  3. Authorization: Bearer ... — le jeton d'authentification. Il est renvoyé à chaque requête, puisque le serveur ne se souvient de rien.
  4. Le corps (body) — les données envoyées, en JSON. GET et DELETE n'en ont pas ; POST, PUT et PATCH en ont un.
  5. En réponse, 201 Created annonce la création, et l'en-tête Location indique où trouver la ressource nouvellement créée.

Les trois étages du code

Le premier chiffre suffit à comprendre : 2 = c'est bon, 4 = c'est de votre faute, 5 = c'est de la nôtre.

⚠️ Le piège du « 200 qui contient une erreur »

Renvoyer 200 OK avec un corps { "erreur": "client introuvable" } est une faute courante et pénible. Le client automatisé, lui, ne lit que le code : il croira que tout va bien. Le code de statut fait partie du contrat, au même titre que le JSON.

💡 401 ou 403 ?

Une phrase pour ne plus hésiter : 401, je ne sais pas qui vous êtes ; 403, je sais qui vous êtes et c'est non.

JSON, le format d'échange

JSON (JavaScript Object Notation) est le format de texte utilisé pour transporter les données. Il est lisible par un humain et par tous les langages.

// La représentation JSON d'un client
{
  "id": 42,
  "nom": "Dupont",
  "email": "d@ex.fr",
  "dateInscription": "2026-03-14",
  "commandes": [1001, 1002]
}

Ce texte n'est pas un objet Java : c'est sa représentation. Le passage de l'un à l'autre porte deux noms que vous croiserez souvent : la sérialisation (objet → texte) et la désérialisation (texte → objet). Le framework s'en charge.

Sans état : la conséquence pratique

Le serveur ne garde rien entre deux requêtes. Cela a une conséquence directe sur l'authentification : il n'y a pas de « session ouverte » côté serveur. Le client renvoie son jeton (token) à chaque appel, dans l'en-tête Authorization.

🎯 Pourquoi c'est un avantage

Parce qu'aucun serveur n'est propriétaire de votre conversation, on peut en démarrer dix identiques derrière un répartiteur de charge. N'importe lequel peut traiter n'importe quelle requête — comme n'importe quel distributeur du hall.

Le flux CRUD de bout en bout

Le schéma le plus important de la séance : ce qui se passe entre le clic de l'utilisateur et la ligne dans PostgreSQL.

Vous avez maintenant toutes les pièces. Assemblons-les. Les quatre opérations CRUD suivent exactement le même trajet : elles entrent par l'API, traversent les trois couches et finissent en SQL.

Le grand schéma

🎯 Ce que ce schéma vous dit

Quatre opérations, un seul trajet. Quand vous saurez écrire une ligne de ce tableau, vous saurez écrire les trois autres : seuls le verbe, le nom de la méthode et la requête SQL changent. C'est ce qui rend une API CRUD si rapide à produire avec un framework.

Le parcours de la donnée

La donnée ne traverse pas ces couches sans changer de forme. Elle est transformée quatre fois, et chaque transformation a un nom que vous entendrez.

⚠️ Quatre formes, quatre noms — ne les mélangez pas

Le JSON est du texte. Le DTO est un objet fait pour entrer et sortir. L'entité est un objet fait pour le domaine et la base. La ligne est ce qui existe réellement dans PostgreSQL. Utiliser une entité comme DTO, c'est ouvrir sa réserve aux clients ; utiliser un DTO comme entité, c'est confier ses règles métier à la salle.

Une création, pas à pas

Suivons une seule requête, POST /clients, du début à la fin.

// ÉTAPE 1-2 — le framework reçoit le texte et fabrique un DTO
//   { "nom": "Dupont", "email": "d@ex.fr" }  →  CreerClientDto

// ÉTAPE 3 — le CONTRÔLEUR reçoit l'objet, ne décide rien
@PostMapping("/clients")
public ResponseEntity<ClientDto> creer(@RequestBody CreerClientDto dto) {
    Client cree = service.creer(dto.nom(), dto.email());   // il délègue
    return ResponseEntity
             .status(201)                                // le bon code
             .body(ClientDto.depuis(cree));               // un DTO, pas l'entité
}

// ÉTAPE 4 — le SERVICE décide
public Client creer(String nom, String email) {
    if (repository.existsByEmail(email)) {              // règle métier
        throw new EmailDejaUtilise(email);                // → deviendra un 409
    }
    Client client = new Client(nom, email);            // l'entité
    return repository.save(client);                     // il délègue à son tour
}

// ÉTAPE 5-6 — le REPOSITORY et l'ORM produisent le SQL
//   INSERT INTO client (nom, email, date_inscription) VALUES (?, ?, ?)
//   → PostgreSQL attribue l'id 42

// ÉTAPE 7 — la réponse repart : entité → DTO → JSON
//   201 Created + { "id": 42, "nom": "Dupont", "email": "d@ex.fr" }

Analysons ce parcours étape par étape :

  1. Désérialisation — le framework transforme le texte JSON en CreerClientDto. Vous n'écrivez pas cette ligne : @RequestBody la déclenche.
  2. Contrôleur — il ne teste rien, ne calcule rien. Il appelle le service et choisit le code de statut. Trois lignes, c'est normal.
  3. Service — c'est ici, et nulle part ailleurs, que vit la règle « un e-mail ne peut pas servir deux fois ». Elle est testable sans base et sans réseau.
  4. Repository — save() ne contient aucune décision. L'ORM traduit en INSERT.
  5. Retour — l'entité repart en DTO, puis en JSON. L'entité elle-même ne sort jamais de l'application.
💡 Le réflexe de placement

Devant n'importe quelle ligne de code à écrire, posez-vous une seule question : « est-ce que c'est une décision ? » Si oui, elle va dans le service. Si c'est de la traduction (JSON, codes HTTP, formats), elle va dans le contrôleur. Si c'est du rangement, elle va dans le repository.

Deux ponts vers Spring Boot

Deux mécanismes qui relient tout ce qui précède à ce que vous ouvrirez la semaine prochaine.

L'injection de dépendances

On rebranche la prise

Vous ne produisez pas votre électricité : vous branchez. Mieux, dans une maison neuve, vous ne posez pas non plus les câbles — l'installation existe, vous n'avez qu'à brancher.

Le conteneur IoC de Spring, c'est cette installation électrique : il fabrique les objets et les branche les uns aux autres à votre place.

En 3.4, nous avons fait entrer la dépendance par le constructeur. Il restait un problème : quelqu'un doit bien écrire le new quelque part.

// AVANT : quelqu'un doit tout assembler à la main
ClientDao dao = new ClientDaoPostgres(connexion);
ClientService service = new ClientService(dao);
ClientController ctrl = new ClientController(service);
// ... et ainsi de suite sur 300 classes
// APRÈS : le conteneur assemble seul
@Service                                  // « je suis un objet à gérer »
public class ClientService {

    private final ClientDao dao;

    public ClientService(ClientDao dao) {  // « il me faut un ClientDao »
        this.dao = dao;                     // Spring le trouve et le fournit
    }
}

Analysons ce code ligne par ligne :

  1. @Service — l'étiquette déclare la classe au conteneur. Au démarrage, Spring parcourt le projet, repère l'étiquette et fabrique un exemplaire de la classe.
  2. ClientService(ClientDao dao) — le constructeur exprime un besoin : « donnez-moi quelque chose qui respecte le contrat ClientDao ».
  3. Spring cherche dans son inventaire une classe qui implémente ce contrat, et la passe automatiquement. Vous n'écrivez plus aucun new.

C'est l'inversion de contrôle de la section 2, appliquée non plus au déroulement du programme mais à la construction des objets.

💡 Injectez toujours par le constructeur

Spring propose trois voies : constructeur, setter, ou directement sur l'attribut avec @Autowired. Préférez systématiquement le constructeur : il rend les dépendances visibles, autorise le final, et permet d'instancier la classe à la main dans un test.

L'ORM

L'interprète

Deux personnes doivent travailler ensemble. L'une parle le langage des tableaux : lignes, colonnes, jointures. L'autre parle le langage des objets : classes, attributs, références. Elles ne se comprennent pas. On engage un interprète, qui traduit dans les deux sens sans jamais participer à la conversation.

Un ORM (Object-Relational Mapping — « correspondance objet-relationnel ») est cet interprète. En Java, la norme s'appelle JPA et l'implémentation la plus répandue Hibernate.

Ce que vous écrivezCe que l'ORM produit
repository.findById(42L)SELECT * FROM client WHERE id = 42
repository.save(client)INSERT ou UPDATE, selon le cas
client.getCommandes()SELECT * FROM commande WHERE id_client = 42

La traduction n'est pas parfaite, parce que les deux mondes ne sont pas superposables. On appelle cet écart le décalage objet-relationnel (impedance mismatch) :

En JavaEn base relationnelleLe problème
L'héritage existeIl n'existe pasIl faut choisir une stratégie de traduction
Deux objets peuvent être égaux sans être le mêmeLa clé primaire trancheDeux notions d'identité différentes
Une référence est à sens uniqueUne jointure se lit dans les deux sensIl faut désigner un côté « propriétaire »
Les collections sont chargées en mémoireUne table peut faire dix millions de lignesQuand charge-t-on ? D'où le chargement paresseux
⚠️ L'ORM ne vous dispense pas de savoir écrire du SQL

Il le rend au contraire plus nécessaire. Un ORM mal utilisé transforme une boucle sur 100 clients en 101 requêtes — c'est le fameux problème « N+1 ». Sans lire le SQL généré, vous ne verrez jamais le problème ; vous constaterez seulement que l'application est lente. Vos séances PostgreSQL vont servir plus que vous ne le pensez.

Où se place Spring Boot

Tout ce qui précède se recompose en une seule image.

Dernier passage sur le chantier

Spring Framework, c'est le constructeur de maisons préfabriquées : il fournit la structure porteuse — le conteneur IoC — et un catalogue d'options. Historiquement, il fallait remplir un long formulaire de configuration pour choisir chaque élément.

Spring Boot, c'est le même constructeur avec un catalogue « clés en main ». Vous cochez maison familiale, il livre chauffage, électricité et cuisine équipée, déjà branchés, aux emplacements standards. Vous restez libre de tout changer — mais si les emplacements standards vous conviennent, vous n'avez rien à faire.

Réflexes et pièges

Les confusions qui reviennent en évaluation et en entretien d'embauche.

 L'affirmation fausseCe qu'il faut répondre
1« Un framework est une grosse bibliothèque »Le critère est le sens de l'appel, pas la taille
2« IoC et injection de dépendances, c'est pareil »L'IoC est le principe, la DI une technique parmi d'autres
3« MVC remplace l'architecture en couches »MVC organise la présentation ; les couches organisent l'application. Les deux coexistent
4« Le M de MVC, c'est la base de données »C'est le domaine : les données et les règles
5« MVVM, c'est pour le desktop »Le vrai critère est la présence d'une liaison de données automatique
6« Une couche et un tier, c'est la même chose »Logique contre physique. Trois couches peuvent tenir sur une machine
7« Les microservices, c'est mieux »C'est un arbitrage organisationnel très coûteux à exploiter
8« Une API, c'est un site web »C'est un contrat. Les méthodes public d'une classe Java en sont une aussi
9« GET /supprimerClient?id=42 »L'adresse nomme une ressource, le verbe dit l'action : DELETE /clients/42
10« POST et PUT, c'est pareil »POST crée à chaque appel ; PUT est idempotent
11« On renvoie 200 avec un message d'erreur »Le code de statut fait partie du contrat : 404, 409, 400…
12« REST garde ma session ouverte »REST est sans état : le jeton repart à chaque requête
13« On peut renvoyer l'entité directement »C'est la fuite de données classique. On passe par un DTO
14« Avec un ORM, plus besoin de SQL »Il en faut davantage : voir le problème N+1
🎯 Les quatre phrases à savoir réciter

1. Une bibliothèque, je l'appelle ; un framework, il m'appelle.
2. Couplage faible, cohésion forte.
3. Chaque couche ne parle qu'à celle du dessous.
4. Une API est un contrat : l'adresse nomme la chose, le verbe dit l'action.
