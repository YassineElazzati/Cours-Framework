Ce qu'on va construire

Une API REST complète pour gérer le catalogue de livres d'une bibliothèque.

À la fin de ce TP, votre application répondra à cinq requêtes HTTP. Les voici, dans l'ordre où nous les ferons fonctionner :

📝 Rappel de la séance passerelle

Le restaurant devient une bibliothèque : mêmes rôles, autre décor. Le contrôleur est le guichet, le service est le bibliothécaire qui connaît le règlement, le repository est le magasinier qui va chercher les ouvrages en réserve. Et le client n'entre jamais dans la réserve.

Dans quel ordre construire — et pourquoi

Nous allons construire de bas en haut : d'abord la donnée, ensuite ce qui la range, puis ce qui décide, enfin ce qui expose. Ce n'est pas un caprice : c'est l'ordre dans lequel le code compile. Un service ne peut pas être écrit avant le repository dont il dépend.

💡 Vous n'aurez rien à l'écran avant la §11

C'est normal et c'est déstabilisant la première fois. Pendant quatre étapes, vous écrivez du code sans rien voir. Tenez bon : à l'étape 5, tout s'allume d'un coup. Les fois suivantes, vous irez trois fois plus vite.

Le domaine : la bibliothèque

Le MCD que vous connaissez, sa traduction en tables, et ce qu'on implémente aujourd'hui.

Le MCD

Le MLD, puis le MPD

📝 La règle que vous avez apprise

Une association (1,1) — (0,n) se traduit par une clé étrangère du côté du 1,1. Une association (1,n) — (1,n) se traduit par une table de jointure supplémentaire. Une association porteuse d'attributs devient toujours une table.

-- MLD, en écriture textuelle
categorie (id_categorie, libelle)
auteur    (id_auteur, nom, prenom)
livre     (id_livre, titre, isbn, annee_publication, nb_pages, #id_categorie)
ecrire    (#id_livre, #id_auteur)
adherent  (id_adherent, nom, prenom, email, date_inscription)
emprunt   (id_emprunt, date_emprunt, date_retour, #id_livre, #id_adherent)

Et le MPD, c'est-à-dire le SQL réellement exécuté par PostgreSQL :

-- Créez d'abord la base, dans psql ou pgAdmin
CREATE DATABASE bibliotheque;

-- Puis, dans cette base :
CREATE TABLE categorie (
    id_categorie  BIGSERIAL PRIMARY KEY,
    libelle       VARCHAR(50) NOT NULL UNIQUE
);

CREATE TABLE auteur (
    id_auteur     BIGSERIAL PRIMARY KEY,
    nom           VARCHAR(60) NOT NULL,
    prenom        VARCHAR(60)
);

CREATE TABLE livre (
    id_livre          BIGSERIAL PRIMARY KEY,
    titre             VARCHAR(200) NOT NULL,
    isbn              VARCHAR(13)  NOT NULL UNIQUE,
    annee_publication INTEGER,
    nb_pages          INTEGER,
    id_categorie      BIGINT NOT NULL
        REFERENCES categorie(id_categorie)     -- la clé étrangère
);

CREATE TABLE ecrire (                          -- la table de jointure
    id_livre   BIGINT REFERENCES livre(id_livre),
    id_auteur  BIGINT REFERENCES auteur(id_auteur),
    PRIMARY KEY (id_livre, id_auteur)            -- clé primaire composée
);
💡 Vous pourriez ne pas écrire ce SQL du tout

Hibernate sait générer ces tables tout seul à partir de vos entités Java — nous le configurerons en §4. Écrivez-les quand même : vous verrez ainsi que la table générée correspond bien à ce que vous aviez modélisé, et vous saurez repérer le jour où ce n'est pas le cas.

Spring Initializr

Le générateur officiel de projets Spring Boot. Trois minutes, et le squelette est prêt.

Le configurateur de voiture

Sur le site d'un constructeur, vous ne dessinez pas votre voiture : vous cochez des options dans un formulaire. Motorisation, finition, couleur, options. Vous cliquez, et l'usine assemble une voiture complète, roulante, cohérente.

Spring Initializr est ce configurateur. Vous cochez « base de données PostgreSQL » et « API web », il vous livre un projet qui démarre.

Rendez-vous sur start.spring.io. La plupart des IDE proposent le même formulaire intégré — dans IntelliJ IDEA : File → New → Project → Spring Boot.

Vous cochez toujours Spring Web dans le formulaire, mais dans le pom.xml généré la dépendance s'appelle désormais spring-boot-starter-webmvc, et non plus spring-boot-starter-web. Le renommage sert à la distinguer de webflux, l'autre modèle de programmation web de Spring.

Conséquence pratique : tous les tutoriels écrits avant fin 2025 affichent l'ancien nom. Ce n'est pas une erreur de leur part, c'est une version antérieure. L'ancien nom fonctionne encore, mais il est déprécié.

Le contrôleur — la porte d'entrée

C'est lui qui reçoit la donnée. Quand une requête HTTP arrive (POST /api/v1/livres avec du JSON), c'est le contrôleur qui décroche. Son travail : traduire le JSON en objet Java, vérifier que le format est correct, puis passer la main au service. Il ne décide rien, il ne contient aucune règle métier, il ne touche jamais à la base. C'est le serveur en salle : il prend la commande et la transmet en cuisine — il ne cuisine pas.

Les DTO — les formulaires officiels

Ce sont les seuls objets qui franchissent la porte, dans les deux sens. CreerLivreRequete définit exactement ce que le client a le droit d'envoyer (et les annotations @NotBlank, @Pattern le contrôlent à l'entrée) ; LivreReponse définit exactement ce que vous acceptez de montrer. Vos entités, elles, ne sortent jamais : on ne fait pas visiter la cuisine aux clients.

Le service — le cerveau

C'est lui qui décide. L'ISBN est-il déjà pris ? La catégorie existe-t-elle ? Peut-on enregistrer ? Toutes les règles du métier vivent ici, et nulle part ailleurs. C'est aussi lui qui ouvre la transaction. Si un jour on vous demande « où est la règle qui interdit deux ISBN identiques ? », la réponse est toujours la même : dans le service. C'est le chef de cuisine : la commande arrive, il vérifie, il tranche.

Le repository — le magasinier

C'est lui qui parle à la base, et personne d'autre. Vous déclarez une interface d'une ligne, et Spring Data JPA écrit le SQL à votre place : save(), findById(), findAll(), deleteById(). Il range et va chercher, sans jamais se demander si la demande est légitime — ce n'est pas son rôle, c'est celui du service. C'est le commis au garde-manger : on lui demande un ingrédient, il le rapporte, point.

Les entités — le miroir de la base

Une entité, c'est une table PostgreSQL vue depuis Java : la classe Livre = la table livre, un objet = une ligne, un attribut = une colonne. Les annotations @Entity, @Column, @ManyToOne apprennent à Hibernate la correspondance exacte avec votre MPD. C'est votre MCD qui a pris vie en code.

Les erreurs — le service réclamations

Quand le service détecte un problème, il lève une exception métier (LivreIntrouvableException…). Le GestionnaireErreurs les intercepte toutes au même endroit et les traduit en réponses HTTP propres : introuvable → 404, ISBN en double → 409, données invalides → 400. Sans lui, le client recevrait un 500 illisible avec la pile d'erreur Java.

🎯 La règle d'or de cette arborescence

Une requête traverse toujours les couches dans le même ordre : contrôleur → service → repository → base, et la réponse remonte en sens inverse. Jamais de raccourci : un contrôleur qui appelle directement un repository, c'est un client qui va se servir dans le garde-manger. Ça marche un jour — c'est le chaos dès que l'application grossit.

Le pom.xml

La fiche d'identité et la liste de courses

Le pom.xml fait deux choses, et deux seulement.

C'est d'abord la carte d'identité du projet : son nom, sa version, la version de Java à utiliser. C'est ensuite la liste de courses : les bibliothèques dont votre code a besoin.

Maven est le livreur. Il lit la liste, va chercher chaque paquet sur un entrepôt public appelé Maven Central, le range dans un placard local (le dossier .m2 de votre compte), et le met à disposition de votre code. Vous n'installez jamais rien à la main.

« POM » signifie Project Object Model — le modèle du projet. Voici le fichier généré, allégé de quelques balises de confort :

<!-- 1. En-tête : c'est un fichier Maven, version 4 du format -->
<project xmlns="http://maven.apache.org/POM/4.0.0">
    <modelVersion>4.0.0</modelVersion>

    <!-- 2. LE PARENT : l'héritage qui fait toute la magie -->
    <parent>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-parent</artifactId>
        <version>4.1.0</version>
    </parent>

    <!-- 3. L'IDENTITÉ de VOTRE projet -->
    <groupId>fr.bibliotheque</groupId>
    <artifactId>api</artifactId>
    <version>0.0.1-SNAPSHOT</version>

    <!-- 4. LES RÉGLAGES -->
    <properties>
        <java.version>21</java.version>
    </properties>

    <!-- 5. LA LISTE DE COURSES -->
    <dependencies>
        <dependency>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-starter-webmvc</artifactId>
        </dependency>
        <dependency>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-starter-data-jpa</artifactId>
        </dependency>
        <dependency>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-starter-validation</artifactId>
        </dependency>

        <dependency>
            <groupId>org.postgresql</groupId>
            <artifactId>postgresql</artifactId>
            <scope>runtime</scope>   <!-- utile à l'exécution seulement -->
        </dependency>
    </dependencies>

    <!-- 6. LE PLUGIN qui fabrique le .jar exécutable -->
    <build>
        <plugins>
            <plugin>
                <groupId>org.springframework.boot</groupId>
                <artifactId>spring-boot-maven-plugin</artifactId>
            </plugin>
        </plugins>
    </build>
</project>

Analysons ce fichier bloc par bloc :

BlocCe qu'il fait réellement
2 · <parent>Le bloc le plus important. Votre pom.xml hérite de celui de Spring Boot, qui contient déjà les versions compatibles de plusieurs centaines de bibliothèques. C'est pour cela que les dépendances suivantes n'ont pas de numéro de version : le parent l'a déjà décidé pour vous, et il a testé que tout fonctionne ensemble
3 · l'identitégroupId + artifactId + version forment les coordonnées uniques du projet, comme une adresse postale. Toute bibliothèque du monde Java se désigne par ces trois valeurs
4 · <properties>Des réglages réutilisables. java.version indique avec quelle version compiler
5 · <dependencies>La liste de courses. Un starter n'est pas une bibliothèque : c'est un lot de bibliothèques cohérentes. spring-boot-starter-data-jpa à lui seul apporte Hibernate, l'API JPA, le pool de connexions et la gestion des transactions
<scope>runtime</scope>Le pilote PostgreSQL n'est pas nécessaire pour compiler — votre code ne le nomme jamais — mais il l'est pour exécuter. Le déclarer ainsi évite qu'un développeur l'utilise par erreur dans le code
6 · le pluginC'est lui qui produit un .jar contenant votre code et le serveur Tomcat et toutes les dépendances. Un seul fichier, lançable par java -jar
🎯 Pourquoi les dépendances n'ont pas de version

Parce que le <parent> les fixe. C'est exactement le principe de convention plutôt que configuration vu à la séance précédente : Spring Boot a choisi pour vous un jeu de versions qui fonctionnent ensemble, et vous n'avez rien à décider. Le jour où vous devrez forcer une version précise, vous l'écrirez explicitement — et vous saurez que vous prenez un risque.

La classe principale

package fr.bibliotheque.api;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;

@SpringBootApplication
public class ApiApplication {

    public static void main(String[] args) {
        SpringApplication.run(ApiApplication.class, args);
    }
}

Analysons ce code ligne par ligne :

  1. @SpringBootApplication — une seule étiquette qui en vaut trois : elle active l'auto-configuration, déclare la classe comme source de configuration, et lance le balayage des paquets à partir d'ici. C'est cette dernière fonction qui explique l'avertissement de la §3.
  2. SpringApplication.run(...) — la seule ligne que vous exécutez vous-même. Elle démarre le conteneur IoC, qui fabrique tous vos objets, puis lance Tomcat.
  3. Après cette ligne, vous n'appelez plus jamais rien. C'est l'inversion de contrôle : à partir d'ici, c'est le framework qui appelle votre code.

La base de données avec Docker Compose (recommandé)

Plutôt que d'installer PostgreSQL sur votre machine, lancez-le dans un conteneur Docker : tout le monde obtient exactement la même base, avec la même version, en une seule commande — et on peut la jeter et la recréer à volonté.

Le meuble en kit déjà monté

Installer PostgreSQL à la main, c'est monter le meuble : télécharger, configurer le mot de passe, créer la base, et déboguer les différences entre le poste de votre voisin et le vôtre.

Docker vous livre le meuble déjà monté : une image contient PostgreSQL installé, configuré, prêt à démarrer. Le fichier docker-compose.yml est le bon de commande : il décrit ce que vous voulez (quelle version, quel mot de passe, quelle base), et docker compose up vous le livre. Même bon de commande = même livraison, sur toutes les machines de la classe.

Créez un fichier docker-compose.yml à la racine du projet (à côté du pom.xml) :

services:
  db:
    image: postgres:17              # la version, figée pour toute la classe
    container_name: bibliotheque-db
    environment:
      POSTGRES_DB: bibliotheque     # la base est créée automatiquement
      POSTGRES_USER: postgres
      POSTGRES_PASSWORD: bibliotheque
    ports:
      - "5432:5432"                  # port du conteneur → port de votre machine
    volumes:
      - pgdata:/var/lib/postgresql/data  # les données survivent aux redémarrages

volumes:
  pgdata:

Puis, dans un terminal ouvert à la racine du projet :

# Démarrer la base (˗d = en arrière-plan)
docker compose up -d

# Vérifier qu'elle tourne
docker compose ps
# → bibliotheque-db   running   0.0.0.0:5432->5432/tcp

# Ouvrir un terminal SQL dans le conteneur (pour vos INSERT de la §11)
docker compose exec db psql -U postgres -d bibliotheque

# Arrêter la base (les données sont conservées)
docker compose down

# Tout effacer et repartir de zéro (données comprises)
docker compose down -v
🎯 Deux choses que Docker fait pour vous

Grâce à POSTGRES_DB: bibliotheque, la base est créée automatiquement au premier démarrage : le CREATE DATABASE de la §2 devient inutile. Et grâce au volume pgdata, vos données survivent à un docker compose down — seul down -v les efface, ce qui est d'ailleurs très pratique pour recommencer un test proprement.

💡 Vous avez déjà PostgreSQL installé ?

Docker n'est pas obligatoire : créez simplement la base à la main (CREATE DATABASE bibliotheque;) et utilisez vos propres identifiants dans application.properties. Attention au conflit de port : si un PostgreSQL local tourne déjà sur 5432, le conteneur ne pourra pas démarrer — changez alors la ligne ports en "5433:5432" et adaptez l'URL JDBC.

La configuration : application.properties

Ouvrez src/main/resources/application.properties. Il est vide. Remplissez-le :

# ── Connexion à PostgreSQL ────────────────────────────────
spring.datasource.url=jdbc:postgresql://localhost:5432/bibliotheque
spring.datasource.username=postgres
spring.datasource.password=bibliotheque  # celui du docker-compose.yml

# ── Comportement de l'ORM ─────────────────────────────────
spring.jpa.hibernate.ddl-auto=update
spring.jpa.show-sql=true
spring.jpa.properties.hibernate.format_sql=true

# ── Serveur ───────────────────────────────────────────────
server.port=8080
PropriétéCe qu'elle règle
spring.datasource.urlL'adresse de la base. jdbc:postgresql:// désigne le protocole, 5432 le port par défaut de PostgreSQL, bibliotheque le nom de la base
ddl-auto=updateHibernate compare vos entités aux tables existantes et crée ce qui manque au démarrage. Très pratique en apprentissage
show-sql=trueAffiche dans la console chaque requête SQL générée. Laissez-le activé pendant tout le TP
format_sql=trueMet le SQL affiché en forme, sur plusieurs lignes
⚠️ ddl-auto : jamais en production

update ne sait qu'ajouter : il ne supprime jamais une colonne devenue inutile et ne renomme rien. Sur un vrai projet, on met validate — Hibernate vérifie que la base correspond aux entités et refuse de démarrer sinon — et l'évolution des tables est confiée à un outil de migration comme Flyway ou Liquibase.

Et surtout : create-drop efface toutes vos tables à chaque arrêt. Ne le tapez pas par curiosité sur une base qui contient quelque chose.

💡 Le mot de passe n'a rien à faire là

Un mot de passe écrit dans un fichier versionné finit sur GitHub. En vrai projet, on utilise une variable d'environnement : spring.datasource.password=${DB_PASSWORD}. Pour ce TP en local, on l'écrit en clair — mais prenez l'habitude de vérifier ce que vous versionnez.

Les entités

Première étape de code : traduire les tables en classes Java.

La fiche cartonnée

Avant l'informatique, une bibliothèque fonctionnait déjà. Chaque ouvrage avait sa fiche cartonnée : titre, ISBN, année, rangée dans le tiroir « LIVRES » du meuble à fiches.

Une entité est cette fiche, en Java. Le tiroir est la table PostgreSQL. Et l'annotation @Entity est l'étiquette collée sur la fiche qui dit : « celle-ci va dans le tiroir LIVRE ».

Créez le paquet fr.bibliotheque.api.entite. Nous y mettrons trois classes.

💡 Un mot sur les noms français

Nous nommons les paquets en français pour que la correspondance avec le MCD saute aux yeux. En entreprise, la convention est l'anglais : entity, repository, service, controller. Les annotations, elles, sont toujours en anglais : ce sont celles de Spring.

Categorie : la plus simple

package fr.bibliotheque.api.entite;

import jakarta.persistence.*;

@Entity                              // « cette classe correspond à une table »
@Table(name = "categorie")          // laquelle, précisément
public class Categorie {

    @Id                                              // la clé primaire
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    @Column(name = "id_categorie")
    private Long id;

    @Column(name = "libelle", nullable = false, length = 50, unique = true)
    private String libelle;

    protected Categorie() { }        // exigé par JPA — voir l'avertissement

    public Categorie(String libelle) {
        this.libelle = libelle;
    }

    public Long getId() { return id; }
    public String getLibelle() { return libelle; }
    public void setLibelle(String libelle) { this.libelle = libelle; }
}

Analysons ce code ligne par ligne :

  1. import jakarta.persistence.* — le paquet de la norme JPA. Attention : les tutoriels d'avant 2023 écrivent javax.persistence. C'est l'ancien nom, il ne compile plus.
  2. @Entity — l'étiquette essentielle. Sans elle, Hibernate ignore totalement la classe : ce n'est plus qu'un objet Java ordinaire.
  3. @Table(name = "categorie") — le nom exact de la table. Sans cette annotation, Hibernate déduirait le nom depuis celui de la classe. On l'écrit explicitement pour rester maître du MPD qu'on a modélisé.
  4. @Id — désigne l'attribut qui porte la clé primaire. Obligatoire : une entité sans @Id fait échouer le démarrage.
  5. @GeneratedValue(strategy = IDENTITY) — « c'est la base qui attribue le numéro, pas moi ». IDENTITY correspond exactement au BIGSERIAL de PostgreSQL.
  6. @Column(name = "id_categorie") — le pont entre le snake_case de SQL et le camelCase de Java. L'attribut s'appelle id, la colonne id_categorie.
  7. nullable = false, length = 50, unique = true — les contraintes, recopiées depuis votre MPD. Elles servent à Hibernate pour générer la table, et documentent l'intention.
  8. protected Categorie() { } — le constructeur sans argument. Hibernate en a besoin pour reconstruire un objet depuis une ligne lue en base. protected plutôt que public : Hibernate y accède, votre code non.
  9. Pas de setter sur id : personne ne doit pouvoir changer une clé primaire à la main.
Le distributeur de tickets

@GeneratedValue, c'est la machine à tickets de la boucherie. Vous ne choisissez pas votre numéro : vous appuyez, la machine vous en donne un, et il est forcément unique. C'est la base qui tient le compteur, jamais votre code.

⚠️ Le constructeur vide oublié

C'est l'erreur numéro un du premier TP. Si vous écrivez un constructeur avec paramètres, Java supprime le constructeur vide par défaut. Hibernate, lui, en a absolument besoin. Le message est cryptique : « No default constructor for entity ». Dès que vous ajoutez un constructeur à une entité, ajoutez aussi le constructeur vide.

Livre : les relations

C'est ici que le MCD devient du code. Deux associations à traduire.

package fr.bibliotheque.api.entite;

import jakarta.persistence.*;
import java.util.HashSet;
import java.util.Set;

@Entity
@Table(name = "livre")
public class Livre {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    @Column(name = "id_livre")
    private Long id;

    @Column(nullable = false, length = 200)
    private String titre;

    @Column(nullable = false, unique = true, length = 13)
    private String isbn;

    @Column(name = "annee_publication")
    private Integer anneePublication;

    @Column(name = "nb_pages")
    private Integer nbPages;

    // ── APPARTENIR : (1,1) côté LIVRE → une clé étrangère ──────
    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "id_categorie", nullable = false)
    private Categorie categorie;

    // ── ECRIRE : (1,n)-(1,n) → une table de jointure ───────────
    @ManyToMany(fetch = FetchType.LAZY)
    @JoinTable(
        name = "ecrire",
        joinColumns        = @JoinColumn(name = "id_livre"),
        inverseJoinColumns = @JoinColumn(name = "id_auteur"))
    private Set<Auteur> auteurs = new HashSet<>();

    protected Livre() { }

    public Livre(String titre, String isbn, Integer annee, Categorie categorie) {
        this.titre = titre;
        this.isbn = isbn;
        this.anneePublication = annee;
        this.categorie = categorie;
    }

    public void ajouterAuteur(Auteur auteur) {
        this.auteurs.add(auteur);
    }

    public Long getId()                  { return id; }
    public String getTitre()             { return titre; }
    public String getIsbn()              { return isbn; }
    public Integer getAnneePublication() { return anneePublication; }
    public Integer getNbPages()          { return nbPages; }
    public Categorie getCategorie()      { return categorie; }
    public Set<Auteur> getAuteurs()      { return auteurs; }

    public void setTitre(String titre)   { this.titre = titre; }
    public void setAnneePublication(Integer a) { this.anneePublication = a; }
    public void setNbPages(Integer n)   { this.nbPages = n; }
    public void setCategorie(Categorie c) { this.categorie = c; }
}

Analysons les deux relations, ligne par ligne :

La relation vers Categorie

  1. @ManyToOne — se lit dans ce sens : plusieurs livres pour une catégorie. C'est la traduction directe du (1,1) côté LIVRE dans le MCD.
  2. @JoinColumn(name = "id_categorie") — indique quelle colonne porte la clé étrangère, dans la table livre. Sans cette annotation, Hibernate inventerait un nom de colonne.
  3. optional = false — un livre a forcément une catégorie. C'est le 1,1 du MCD, exprimé en Java.
  4. Notez le type : Categorie categorie, pas Long idCategorie. C'est tout l'intérêt de l'ORM : vous manipulez un objet, pas un numéro. livre.getCategorie().getLibelle() fonctionne, sans que vous n'écriviez la moindre jointure.

La relation vers Auteur

  1. @ManyToMany — plusieurs livres pour plusieurs auteurs. La traduction du (1,n)-(1,n).
  2. @JoinTable(name = "ecrire") — le nom de la table de jointure, celle que vous aviez déduite du MCD.
  3. joinColumns — la colonne qui pointe vers cette entité, celle où l'on est : id_livre.
  4. inverseJoinColumns — la colonne qui pointe vers l'autre entité : id_auteur. La confusion entre ces deux paramètres est fréquente ; retenez « join = moi, inverse = l'autre ».
  5. Set<Auteur> plutôt que List<Auteur> — un même auteur ne peut pas écrire deux fois le même livre. Le Set l'interdit par construction, et évite des doublons désagréables.
  6. = new HashSet<>() — la collection est initialisée dès la déclaration. Sans cela, ajouterAuteur déclencherait un NullPointerException sur un livre neuf.

⚠️ LAZY, EAGER, et l'erreur que vous allez rencontrer

fetch = LAZY signifie : « ne va chercher les auteurs en base que si on me les demande vraiment ». C'est la bonne pratique — cela évite de charger la moitié de la base à chaque lecture.

Mais si vous appelez livre.getAuteurs() après la fin de la transaction, Hibernate n'a plus de connexion pour aller les chercher, et lève une LazyInitializationException. Nous réglerons ce point proprement en §6 avec une requête de chargement explicite. Retenez pour l'instant que l'erreur existe et d'où elle vient.

⚠️ Ne mettez jamais la relation inverse « pour faire joli »

La tentation est grande d'ajouter List<Livre> livres dans Categorie avec @OneToMany. Ne le faites pas tant que vous n'en avez pas besoin : chaque relation bidirectionnelle est une source de sérialisation infinie en JSON — le livre contient sa catégorie, qui contient ses livres, qui contiennent leur catégorie… Ajoutez la relation inverse le jour où une fonctionnalité l'exige.

🎯 Ce que vous venez de faire

Vous avez décrit vos tables une seule fois, en Java. Hibernate saura désormais lire, écrire et joindre ces tables sans que vous écriviez une ligne de SQL. Relancez l'application : dans la console, vous devriez voir défiler les create table qu'Hibernate exécute.

Le repository

La couche qui parle à la base. C'est l'étape la plus courte du TP — et la plus surprenante.

Le magasinier

Vous embauchez un magasinier pour la réserve. Vous n'avez pas besoin de lui expliquer comment ranger un livre, comment le retrouver par son numéro, comment compter le stock ou comment jeter un exemplaire abîmé : il sait déjà. Ces gestes sont son métier.

Vous ne lui apprenez que ce qui est propre à votre bibliothèque : « ici, on classe aussi par fragment de titre ».

Créez le paquet fr.bibliotheque.api.repository. Voici le fichier complet :

package fr.bibliotheque.api.repository;

import fr.bibliotheque.api.entite.Livre;
import org.springframework.data.jpa.repository.JpaRepository;
import org.springframework.data.jpa.repository.Query;

import java.util.List;
import java.util.Optional;

public interface LivreRepository extends JpaRepository<Livre, Long> {

    // 1. Méthode déduite du nom : Spring écrit le SQL tout seul
    boolean existsByIsbn(String isbn);

    // 2. Idem, avec un LIKE insensible à la casse
    List<Livre> findByTitreContainingIgnoreCase(String fragment);

    // 3. Chargement explicite des relations (voir l'avertissement §5)
    @Query("select l from Livre l " +
           "join fetch l.categorie " +
           "left join fetch l.auteurs")
    List<Livre> listerAvecDetails();

    @Query("select l from Livre l " +
           "join fetch l.categorie " +
           "left join fetch l.auteurs " +
           "where l.id = :id")
    Optional<Livre> trouverAvecDetails(Long id);
}

Analysons ce code ligne par ligne :

  1. public interface — c'est une interface, pas une classe. Vous n'écrirez jamais son implémentation : Spring Data la génère au démarrage et l'enregistre dans le conteneur IoC. C'est le moment le plus déroutant du TP.
  2. extends JpaRepository<Livre, Long> — deux paramètres de généricité : le type de l'entité gérée, et le type de sa clé primaire. Cet extends vous offre d'un coup toutes les méthodes du tableau ci-dessous.
  3. existsByIsbn(String isbn) — une méthode déduite du nom (derived query method). Spring lit le nom, le découpe en mots-clés — exists, By, Isbn — et fabrique SELECT COUNT(*) FROM livre WHERE isbn = ?. Vous n'écrivez que la signature.
  4. findByTitreContainingIgnoreCase — même mécanisme : Containing produit un LIKE %...%, IgnoreCase ajoute un LOWER(). Le nom de la méthode est la requête.
  5. @Query(...) — quand le nom ne suffit plus, on écrit la requête en JPQL. Ce n'est pas du SQL : on y nomme les classes et les attributs Java (Livre, l.categorie), pas les tables et colonnes. Hibernate traduira.
  6. join fetch — la clé du problème signalé en §5. Cela demande à Hibernate de charger le livre et sa catégorie et ses auteurs en une seule requête. Plus de LazyInitializationException, et surtout : plus de problème N+1.
  7. left join fetch pour les auteurs — le left conserve les livres qui n'ont encore aucun auteur. Un join simple les ferait disparaître du résultat.
  8. Optional<Livre> — le type qui dit « peut-être un livre, peut-être rien ». Il oblige l'appelant à traiter le cas absent, au lieu de renvoyer null et de laisser exploser plus loin.
📝 Le problème N+1, souvenez-vous

Sans join fetch, lister 100 livres puis afficher la catégorie de chacun déclenche 1 requête pour la liste, puis 100 requêtes pour les catégories. C'est le problème N+1 vu à la séance précédente. La console avec show-sql=true vous le montre immédiatement : vous voyez 101 select défiler.

🎯 Pourquoi cette couche est si courte

Parce qu'elle ne prend aucune décision. Le magasinier ne juge pas ce qu'on lui demande. Si votre repository contient un if, une règle de gestion ou un calcul, c'est qu'une ligne s'est trompée d'étage : elle appartient au service.

Le service

La couche qui décide. C'est le cœur de votre application.

Le bibliothécaire

Le magasinier sait aller chercher un livre. Le bibliothécaire, lui, connaît le règlement : on ne référence pas deux fois le même ISBN, on ne supprime pas un ouvrage emprunté, on refuse une fiche incomplète.

Il ne range rien lui-même — il demande au magasinier. Mais c'est lui qui dit oui ou non.

Le service

package fr.bibliotheque.api.service;

import fr.bibliotheque.api.entite.Categorie;
import fr.bibliotheque.api.entite.Livre;
import fr.bibliotheque.api.erreur.*;
import fr.bibliotheque.api.repository.CategorieRepository;
import fr.bibliotheque.api.repository.LivreRepository;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

import java.util.List;

@Service                                   // « Spring, fabrique-moi cet objet »
@Transactional(readOnly = true)           // par défaut : lecture seule
public class LivreService {

    private final LivreRepository livreRepository;
    private final CategorieRepository categorieRepository;

    // Injection par constructeur : Spring fournit les deux repositories
    public LivreService(LivreRepository livreRepository,
                        CategorieRepository categorieRepository) {
        this.livreRepository = livreRepository;
        this.categorieRepository = categorieRepository;
    }

    // ── READ ───────────────────────────────────────────────
    public List<Livre> lister() {
        return livreRepository.listerAvecDetails();
    }

    public Livre trouverParId(Long id) {
        return livreRepository.trouverAvecDetails(id)
                .orElseThrow(() -> new LivreIntrouvableException(id));
    }

    // ── CREATE ─────────────────────────────────────────────
    @Transactional                          // écriture : on lève readOnly
    public Livre creer(String titre, String isbn,
                       Integer annee, Long idCategorie) {

        if (livreRepository.existsByIsbn(isbn)) {      // RÈGLE MÉTIER n°1
            throw new IsbnDejaUtiliseException(isbn);
        }

        Categorie categorie = categorieRepository.findById(idCategorie)
                .orElseThrow(() -> new CategorieIntrouvableException(idCategorie));

        Livre livre = new Livre(titre, isbn, annee, categorie);
        return livreRepository.save(livre);
    }

    // ── UPDATE ─────────────────────────────────────────────
    @Transactional
    public Livre modifier(Long id, String titre, Integer annee) {
        Livre livre = trouverParId(id);     // lève 404 si absent
        livre.setTitre(titre);
        livre.setAnneePublication(annee);
        return livre;                        // pas de save() — voir ci-dessous
    }

    // ── DELETE ─────────────────────────────────────────────
    @Transactional
    public void supprimer(Long id) {
        if (!livreRepository.existsById(id)) {
            throw new LivreIntrouvableException(id);
        }
        livreRepository.deleteById(id);
    }
}

Analysons ce code ligne par ligne :

  1. @Service — l'étiquette qui inscrit la classe au conteneur IoC. Techniquement identique à @Component, mais elle documente l'intention : « ceci est de la logique métier ».
  2. private final sur les deux repositories — final garantit qu'ils ne changeront jamais après la construction. C'est le « D » de SOLID appliqué.
  3. Le constructeur — vous n'écrivez aucun new LivreRepository(). Spring voit les paramètres, cherche dans son inventaire, et injecte. Un seul constructeur suffit : depuis Spring 4.3, @Autowired est inutile dans ce cas.
  4. orElseThrow(...) — la manière propre de déballer un Optional. Si le livre existe, on l'obtient ; sinon, l'exception part.
  5. existsByIsbn avant la création — la règle métier. Elle est ici, dans le service, et nulle part ailleurs. Le contrôleur l'ignore ; le repository l'ignore.
  6. new Livre(...) — on construit l'entité avec l'objet Categorie complet, pas avec son identifiant. C'est le monde objet.
  7. save(livre) — l'INSERT. Après cet appel, livre.getId() contient le numéro attribué par PostgreSQL.
  8. modifier ne rappelle pas save(). Ce n'est pas un oubli : voir l'encadré suivant.
  9. supprimer vérifie l'existence avant de supprimer, pour pouvoir répondre 404 plutôt qu'un succès trompeur.
Le chariot à la caisse

Une transaction, c'est le chariot au moment de payer. Soit tout passe en caisse et vous repartez avec, soit un problème survient et vous reposez l'ensemble : on ne sort jamais du magasin avec la moitié des courses payées.

@Transactional pose ce chariot autour d'une méthode. Si une exception survient au milieu, tout ce qui a été écrit en base est annulé.

🎯 Pourquoi modifier() n'appelle pas save()

Parce que pendant une transaction, Hibernate surveille les entités qu'il a chargées. À la fin de la méthode, il compare leur état à celui du chargement, repère les attributs modifiés, et émet l'UPDATE tout seul. On appelle cela le suivi des modifications (dirty checking).

Écrire save() ici ne serait pas une faute — simplement inutile. Mais comprendre ce mécanisme vous évitera de chercher pendant une heure pourquoi une donnée a changé en base « toute seule ».

⚠️ @Transactional(readOnly = true) au niveau de la classe

C'est une bonne pratique : par défaut, tout est en lecture seule, ce qui permet à Hibernate d'optimiser. On lève ensuite explicitement la restriction sur les trois méthodes qui écrivent. Si vous oubliez le @Transactional sur creer, l'INSERT échouera — et vous saurez immédiatement pourquoi.

Ajoutez enfin la troisième exception, sur le même modèle que les deux premières :

Les DTO

Ce qui entre, ce qui sort. Jamais l'entité elle-même.

La fiche photocopiée

La fiche cartonnée de la réserve porte tout : le prix d'achat, le nom du fournisseur, la mention « exemplaire abîmé, à ne pas prêter ». Vous n'allez pas la tendre au lecteur qui vous demande un renseignement.

Vous en faites une photocopie où ne figurent que le titre, l'auteur et l'année. C'est un DTO.

Créez le paquet fr.bibliotheque.api.dto. Nous utilisons des records : une forme de classe Java, disponible depuis Java 16, faite pour transporter des données immuables. Une ligne remplace une trentaine.

Ce qui entre : les requêtes

package fr.bibliotheque.api.dto;

import jakarta.validation.constraints.*;

public record CreerLivreRequete(

        @NotBlank(message = "Le titre est obligatoire")
        @Size(max = 200, message = "200 caractères maximum")
        String titre,

        @NotBlank(message = "L'ISBN est obligatoire")
        @Pattern(regexp = "\\d{13}", message = "L'ISBN doit contenir 13 chiffres")
        String isbn,

        @Min(value = 1450, message = "Année invalide")
        Integer anneePublication,

        @NotNull(message = "La catégorie est obligatoire")
        Long idCategorie
) { }

Analysons ce code ligne par ligne :

  1. public record — Java génère automatiquement le constructeur, les accesseurs (titre(), isbn()…), equals, hashCode et toString. Les champs sont définitifs : un DTO ne se modifie pas.
  2. Les accesseurs s'appellent titre(), pas getTitre(). C'est la convention des records.
  3. @NotBlank — refuse null, la chaîne vide et les chaînes d'espaces. Pour les chaînes de caractères, préférez-le toujours à @NotNull.
  4. @Pattern(regexp = "\\d{13}") — exactement treize chiffres. Le double antislash est nécessaire : en Java, \\d dans le code source produit le \d de l'expression régulière.
  5. @NotNull sur idCategorie — ici c'est un Long, pas une chaîne : @NotBlank ne s'applique pas.
  6. Chaque message sera renvoyé tel quel au client en cas d'erreur. Écrivez-les en français, ils sont lus par des humains.
  7. Le DTO ne contient que ce qu'un client a le droit d'envoyer. Notez l'absence de id : le client ne choisit pas la clé primaire.

public record ModifierLivreRequete(

        @NotBlank(message = "Le titre est obligatoire")
        @Size(max = 200)
        String titre,

        @Min(value = 1450, message = "Année invalide")
        Integer anneePublication
) { }
⚠️ Pourquoi deux DTO différents ?

Parce qu'on ne crée pas et on ne modifie pas les mêmes champs. À la création, l'ISBN et la catégorie sont obligatoires. À la modification, l'ISBN ne doit pas pouvoir changer — c'est l'identité commerciale de l'ouvrage. Un DTO unique vous obligerait à rendre tout facultatif, et vous perdriez la validation.

Ce qui sort : la réponse

package fr.bibliotheque.api.dto;

import fr.bibliotheque.api.entite.Livre;
import java.util.List;

public record LivreReponse(
        Long id,
        String titre,
        String isbn,
        Integer anneePublication,
        String categorie,
        List<String> auteurs
) {

    // Fabrique : transforme une entité en réponse
    public static LivreReponse depuis(Livre livre) {
        return new LivreReponse(
                livre.getId(),
                livre.getTitre(),
                livre.getIsbn(),
                livre.getAnneePublication(),
                livre.getCategorie().getLibelle(),      // on aplatit
                livre.getAuteurs().stream()
                     .map(a -> a.getPrenom() + " " + a.getNom())
                     .toList()
        );
    }
}

Analysons ce code ligne par ligne :

  1. String categorie — pas Categorie categorie. On aplatit : le client reçoit "Roman", pas un objet imbriqué avec un identifiant technique. La réponse JSON en devient beaucoup plus lisible.
  2. List<String> auteurs — même principe : une liste de noms formatés, pas des objets Auteur.
  3. public static LivreReponse depuis(Livre) — une fabrique. Le code de conversion vit à un seul endroit ; le contrôleur écrira simplement LivreReponse.depuis(livre).
  4. livre.getCategorie().getLibelle() — cet appel ne fonctionne que parce que le repository a utilisé join fetch. Sans lui : LazyInitializationException. Tout se tient.
  5. .stream().map(...).toList() — on parcourt le Set<Auteur> et on produit une liste de chaînes.
🎯 La règle absolue

Une entité ne sort jamais du contrôleur, et n'y entre jamais. Le DTO est la frontière. C'est ce qui vous permet d'ajouter demain un champ « prix d'achat » dans Livre sans le publier accidentellement sur Internet.

Le contrôleur REST

Le guichet. Cinq méthodes, et l'API existe.

Le guichet d'accueil

Le lecteur arrive au guichet. L'agent ne cherche pas les livres lui-même et ne connaît pas le règlement par cœur : il écoute la demande, la transmet au bibliothécaire, et rend la réponse.

Son métier est la traduction : transformer une demande venue de l'extérieur en appel interne, et l'inverse.

Créez le paquet fr.bibliotheque.api.controleur :

package fr.bibliotheque.api.controleur;

import fr.bibliotheque.api.dto.*;
import fr.bibliotheque.api.entite.Livre;
import fr.bibliotheque.api.service.LivreService;
import jakarta.validation.Valid;
import org.springframework.http.HttpStatus;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.*;

import java.net.URI;
import java.util.List;

@RestController
@RequestMapping("/api/v1/livres")      // préfixe commun aux 5 adresses
public class LivreController {

    private final LivreService service;

    public LivreController(LivreService service) {
        this.service = service;
    }

    // ── GET /api/v1/livres ─────────────────────────────────
    @GetMapping
    public List<LivreReponse> lister() {
        return service.lister().stream()
                      .map(LivreReponse::depuis)
                      .toList();
    }

    // ── GET /api/v1/livres/42 ──────────────────────────────
    @GetMapping("/{id}")
    public LivreReponse detail(@PathVariable Long id) {
        return LivreReponse.depuis(service.trouverParId(id));
    }

    // ── POST /api/v1/livres ────────────────────────────────
    @PostMapping
    public ResponseEntity<LivreReponse> creer(
            @Valid @RequestBody CreerLivreRequete requete) {

        Livre cree = service.creer(
                requete.titre(),
                requete.isbn(),
                requete.anneePublication(),
                requete.idCategorie());

        return ResponseEntity
                .created(URI.create("/api/v1/livres/" + cree.getId()))
                .body(LivreReponse.depuis(cree));
    }

    // ── PUT /api/v1/livres/42 ──────────────────────────────
    @PutMapping("/{id}")
    public LivreReponse modifier(
            @PathVariable Long id,
            @Valid @RequestBody ModifierLivreRequete requete) {

        return LivreReponse.depuis(
                service.modifier(id, requete.titre(), requete.anneePublication()));
    }

    // ── DELETE /api/v1/livres/42 ───────────────────────────
    @DeleteMapping("/{id}")
    @ResponseStatus(HttpStatus.NO_CONTENT)     // 204
    public void supprimer(@PathVariable Long id) {
        service.supprimer(id);
    }
}

Analysons ce code ligne par ligne :

ÉlémentCe qu'il fait
@RestControllerDeux choses à la fois : déclare la classe au conteneur, et indique que chaque valeur renvoyée doit être convertie en JSON et écrite directement dans la réponse HTTP
@RequestMapping("/api/v1/livres")Le préfixe commun. Les cinq méthodes s'y ajoutent. Notez le v1 : le versionnement de l'API, dès le premier jour
@GetMapping (sans argument)Répond sur l'adresse du préfixe exactement : GET /api/v1/livres
@GetMapping("/{id}")Les accolades désignent une partie variable de l'adresse

🎯 Regardez ce que ce contrôleur ne fait pas

Aucun if. Aucun calcul. Aucun SQL. Aucune règle. Cinq méthodes de trois à six lignes, qui traduisent et délèguent. Si votre contrôleur grossit, c'est que du métier s'y est glissé. C'est le meilleur indicateur de santé de votre architecture.

⚠️ @RestController et @Controller ne sont pas la même chose

@Controller, utilisé seul, fait que la valeur renvoyée est interprétée comme un nom de vue à afficher — c'est le MVC côté serveur qui rend du HTML. @RestController équivaut à @Controller + @ResponseBody : la valeur renvoyée est le corps de la réponse. Si votre API renvoie 404 avec un message parlant de vue introuvable, vous avez oublié le Rest.

La gestion des erreurs

Traduire les exceptions métier en codes HTTP. Une classe, et c'est réglé pour toute l'application.

Le service des réclamations

Quand quelque chose se passe mal au guichet, l'agent n'improvise pas. Il transmet au service des réclamations, un bureau unique qui sait répondre poliment à chaque type d'incident, toujours de la même manière.

En l'état, une exception non traitée produit un 500 Internal Server Error — le code qui signifie « c'est notre faute ». Or un livre introuvable n'est pas notre faute : c'est un 404. Corrigeons cela.

package fr.bibliotheque.api.erreur;

import org.springframework.http.HttpStatus;
import org.springframework.web.bind.MethodArgumentNotValidException;
import org.springframework.web.bind.annotation.*;

import java.util.HashMap;
import java.util.Map;

@RestControllerAdvice          // « je surveille TOUS les contrôleurs »
public class GestionnaireErreurs {

    // 404 — la ressource n'existe pas
    @ExceptionHandler({LivreIntrouvableException.class,
                       CategorieIntrouvableException.class})
    @ResponseStatus(HttpStatus.NOT_FOUND)
    public Map<String, String> introuvable(RuntimeException e) {
        return Map.of("erreur", e.getMessage());
    }

    // 409 — conflit avec l'existant
    @ExceptionHandler(IsbnDejaUtiliseException.class)
    @ResponseStatus(HttpStatus.CONFLICT)
    public Map<String, String> conflit(RuntimeException e) {
        return Map.of("erreur", e.getMessage());
    }

    // 400 — les données envoyées sont invalides
    @ExceptionHandler(MethodArgumentNotValidException.class)
    @ResponseStatus(HttpStatus.BAD_REQUEST)
    public Map<String, String> invalide(MethodArgumentNotValidException e) {
        Map<String, String> erreurs = new HashMap<>();
        e.getBindingResult().getFieldErrors()
         .forEach(err -> erreurs.put(err.getField(),
                                     err.getDefaultMessage()));
        return erreurs;
    }
}

Analysons ce code ligne par ligne :

  1. @RestControllerAdvice — cette classe intercepte les exceptions de tous les contrôleurs de l'application. Vous l'écrivez une fois ; elle vaut pour les contrôleurs que vous ajouterez demain.
  2. @ExceptionHandler({A.class, B.class}) — « quand l'une de ces exceptions remonte, exécute cette méthode ». Deux exceptions ici, car elles méritent le même traitement.
  3. @ResponseStatus(HttpStatus.NOT_FOUND) — le code renvoyé. C'est ici, et nulle part ailleurs, que le métier est traduit en HTTP.
  4. Map.of("erreur", e.getMessage()) — un petit dictionnaire, converti en {"erreur": "Aucun livre avec l'identifiant 99"}.
  5. MethodArgumentNotValidException — l'exception que Spring lève quand @Valid échoue. Elle n'est pas à vous : elle vient du framework.
  6. getBindingResult().getFieldErrors() — la liste des champs fautifs. On les transforme en dictionnaire champ → message, pour que le client sache exactement quoi corriger.

💡 Pour aller plus loin : ProblemDetail

Spring propose depuis la version 6 une classe ProblemDetail, qui met en forme les erreurs selon un format normalisé (RFC 9457) : type, titre, statut, détail, instance. C'est ce qu'on utilise en production, car les clients savent le lire sans documentation. Le Map suffit pour ce TP ; retenez le nom.

⚠️ Ne mettez pas de try/catch dans le contrôleur

La tentation est d'entourer chaque appel de service d'un try/catch pour renvoyer le bon code. Vous obtiendriez cinq blocs identiques, puis dix, puis cinquante. Laissez l'exception remonter : c'est précisément le rôle du @RestControllerAdvice de l'attraper.

Tester avec Postman, pas à pas

curl est parfait pour comprendre, mais taper du JSON dans un terminal devient vite pénible — surtout sous Windows, où PowerShell interprète les guillemets à sa façon. Postman est l'outil standard du métier pour tester une API : une interface graphique où chaque requête est un formulaire qu'on remplit une fois et qu'on rejoue à volonté.

Étape A — Installer et préparer

  1. Téléchargez Postman sur postman.com/downloads et installez-le (compte gratuit, ou mode « lightweight API client » sans compte).
  2. Cliquez sur New → Collection et nommez-la Bibliothèque API. Une collection, c'est un classeur qui regroupe vos requêtes : vous les écrivez une fois, vous les rejouez à chaque modification du code.

Étape B — Votre première requête : la liste des livres

  1. Dans la collection, cliquez sur Add request, nommez-la Lister les livres.
  2. Vérifiez que le menu déroulant à gauche de la barre d'adresse affiche GET.
  3. Dans la barre d'adresse, tapez http://localhost:8080/api/v1/livres.
  4. Cliquez sur Send. En bas : le corps de la réponse (le JSON), et à droite le code 200 OK avec le temps de réponse.

Étape C — Envoyer du JSON : le POST

C'est la seule manipulation nouvelle, retenez-la bien :

  1. Nouvelle requête Créer un livre, méthode POST, même adresse http://localhost:8080/api/v1/livres.
  2. Ouvrez l'onglet Body (sous la barre d'adresse), cochez raw, et dans le menu déroulant à droite choisissez JSON — c'est lui qui ajoute l'en-tête Content-Type: application/json à votre place.
  3. Collez le corps de la requête :
{
    "titre": "Le Nom de la rose",
    "isbn": "9782253033134",
    "anneePublication": 1980,
    "idCategorie": 1
}
  1. Cliquez sur Send : vous devez obtenir 201 Created et le livre créé en JSON. Ouvrez l'onglet Headers de la réponse : l'en-tête Location vous donne l'adresse du nouveau livre.

Étape D — Compléter la collection

Créez les trois requêtes restantes sur le même modèle. Votre collection finale :

Étape E — Rejouer les trois cas d'erreur

  1. 404 — dupliquez Lire un livre (clic droit → Duplicate) et remplacez le 1 par 9999.
  2. 409 — renvoyez Créer un livre une deuxième fois sans rien changer : l'ISBN est déjà pris.

💡 Le réflexe à prendre : lire le code AVANT le corps

À chaque Send, regardez d'abord le code de statut en haut à droite de la réponse : c'est lui qui dit si tout va bien (2xx), si le client s'est trompé (4xx) ou si votre serveur a un bug (5xx). Un 200 avec un corps vide et un 500 avec un long message ne racontent pas du tout la même histoire.
